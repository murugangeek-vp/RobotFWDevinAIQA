# Bank Data Migration Verification — Architecture and Security Decisions

Scope: verify a full data migration from **Webster Bank (source, extracts in Amazon S3)**
to **Santander (target, Snowflake)**. The migration ETL is owned by the bank's migration
team. This framework is **verification-only**: it reads the S3 extracts and the Snowflake
target with read-only identities and produces auditable PASS/FAIL evidence per table.

> Nothing in this repository is specific knowledge of either bank's real systems, schemas,
> volumes, or controls. Every bank-specific value (bucket, account, schema, table/column
> names, code mappings, control totals) is configuration that must come from the migration
> team's approved source-to-target mapping. Repository fixtures are **synthetic**.

## 1. Flow

```text
Webster extract (S3, versioned)          Santander (Snowflake)
s3://<bucket>/<table>/part-*.csv  --ETL-->  <DB>.<SCHEMA>.<TABLE>
        |   (owned by migration team)              |
        +------ read-only ------+   +--- read-only role, no secondary roles
                                v   v
             manifest -> per-table contracts -> Robot suite (expanded per table)
                                |
                 migration_report.json + .sha256  +  Robot report/log
```

## 2. Building blocks

| Block | Location | Purpose |
|---|---|---|
| Migration manifest | `config/migration/*.yaml` | Tables in scope, contract per table, tier, dependencies, cross-table relationships |
| Contracts | `config/contracts/migration/*.yaml` | Columns, keys, DQ rules, transforms, code mappings, control totals, PII flags |
| Environments | `config/environments/migration_*.yaml` | S3 connection + target connection per environment; no secrets |
| Engine | `libs/engine/*`, `libs/migration/*` | Rules, transforms, comparison, controls, integrity, masking, audit |
| Robot | `libs/robot/MigrationLibrary.py`, `tests/migration/` | Declarative per-table tests generated from the manifest |

Adding table 51 = add one contract + one manifest entry. No code or suite changes.

## 3. Verification levels per table

| Level | Check | Execution |
|---|---|---|
| L0 | S3 object lineage (key, VersionId, ETag, size) captured, header/part consistency | S3 API |
| L1 | Source DQ rules (not-null, type, length, range, allowed values, regex, unique, mapping completeness) | Python on extract |
| L2 | Target schema (columns/order, types, nullability, PK) | `INFORMATION_SCHEMA` |
| L3 | Row count source vs target; control totals (count/sum/min/max/null_count, optional group-by) | Aggregate SQL pushed down to target; exact `Decimal` on source |
| L4 | Referential integrity across tables (orphans) in source and target | Anti-join pushed down to target |
| L5 | Full key-based record comparison incl. transforms | Bounded by `max_rows`; fails closed above it |

L5 above the row bound is **not yet supported** (see TODO MIG-P2: chunked hashing). Until
then, tables above the bound are verified at L0–L4 only and the report says so explicitly.

## 4. Security decisions (non-negotiable defaults)

1. **Read-only everywhere.** Snowflake: dedicated SELECT-only role, explicit primary role,
   `USE SECONDARY ROLES NONE`, arbitrary SQL disabled; only fixed, identifier-validated
   aggregate/anti-join queries generated by the adapter. S3: `s3:GetObject`,
   `s3:GetObjectVersion`, `s3:ListBucket` only.
2. **No customer data in evidence.** Columns flagged `pii: true` are masked in every log,
   report, and failure message. With `RECON_MASK_KEY` set, values become keyed HMAC-SHA256
   tokens (correlatable, not reversible, not dictionary-attackable without the key);
   without it they are fully redacted. Plain hashes are never used (account numbers and
   SSNs are low-entropy and brute-forceable).
3. **Fail closed.** Empty prefix, header mismatch between part files, unknown code mapping,
   missing env variable, row bound exceeded, wrong session role, bucket owner mismatch,
   non-HTTPS custom endpoint → FAIL, never skip/PASS.
4. **Secrets never in repo/config/CLI args.** Key-pair auth for Snowflake; AWS standard
   credential chain (role/SSO preferred over static keys); `RECON_MASK_KEY` from a secret
   store.
5. **Tamper-evident evidence.** Report records run id, git commit, SHA-256 of manifest and
   every contract, S3 VersionIds/ETags, and a `.sha256` of the report itself. Retention in
   an immutable store (e.g. S3 Object Lock) is an operational control owned by the bank.
6. **Synthetic data only outside approved bank environments.** Real extracts must never be
   copied to laptops, trial accounts, CI logs, or this repository.

## 5. Open questions for the migration team (answers change configuration, not code)

| # | Question | Why it matters |
|---|---|---|
| Q1 | Approved source-to-target mapping spec (tables, columns, code mappings)? | Contracts and `mappings:` are generated from it |
| Q2 | S3 layout: single file vs `table/part-*.csv`, deltas, control/trailer files? | `key`/`prefix`/`suffix`; control files give independent expected counts/totals |
| Q3 | Largest table row count and total volume? | Decides when chunked hashing (MIG-P2) is mandatory |
| Q4 | Required control totals per table (e.g. balance by currency/product, count by status)? | `controls:` in contracts |
| Q5 | Which columns are PII/confidential per the bank's data classification? | `pii: true` flags; masking |
| Q6 | Is there a Webster-side opening/closing balance proof for transactions? | Balance-proof check (MIG-P3) |
| Q7 | Snowflake: database/schema naming, verification role name, network policy, where the runner executes (bank-approved host)? | Environment config, CI runner placement |
| Q8 | Evidence retention period and immutable store? | Audit sign-off |
| Q9 | Mock-migration cadence and cutover window SLA? | Scheduling, performance targets |
| Q10 | Timezone of source timestamps and the target `TIMESTAMP_NTZ` convention? | Avoids false diffs at day boundaries |
